# RF Sentinel — Handoff Notes

## What this is
A non-rooted Android app (Kotlin) that passively scans nearby BLE advertisements
and WiFi access points, matches detected MAC addresses against a watchlist of
OUI (vendor) prefixes associated with law-enforcement equipment (body cams,
tasers, surveillance cameras, radios/MDTs), and fires a local notification when
a match is seen. Inspired by the nyanBOX hardware device and the now-defunct
RF Party Android app, itself based on Alan Meekins ("Nullagent")'s DEF CON 31
talk "Snoop Unto Them As They Snoop Unto Us," which first documented Axon's
BLE OUI.

**Scope and intent, unchanged from the original design brief:** passive,
receive-only radio scanning only. No transmission, jamming, spoofing, or
interaction with any detected device. No cloud sync — everything stays on
the device. Legality of passive BLE/WiFi scanning varies by jurisdiction;
this is not legal advice, and the app should keep saying so in its README.

## Status (2026-09-27): builds, lint-clean, verified on an emulator
The project now builds with Gradle 9.6.0, AGP 9.4.0 (built-in Kotlin), KSP 2.3.12
and Room 2.8.5, targeting compileSdk 37 and targetSdk 36. `assembleDebug`,
`testDebugUnitTest` and `lintDebug` all pass, with 0 lint errors. The Gradle
wrapper jar and an adaptive launcher icon are now included.

**Verified on a Pixel emulator running API 37:**
- The permission flow works. FINE and COARSE are requested together, then nearby
  devices, then notifications. Denying notifications still lets scanning start.
- `ScanForegroundService` runs with type `connectedDevice|location` (0x18).
- End-to-end detection: a custom OUI matching the emulator's virtual AP was
  picked up by a WiFi scan, stored in Room and shown in the live feed.
- Long-press to whitelist works. The whitelist and watchlist screens, Settings
  save, and the overflow menu all work.
- The Quick Settings tile starts and stops the service from the home screen. The
  system grants the "tile onclick" allowlist, so it still gets the location type.

**Not verified. Needs a real device:**
- Actual BLE catches. The emulator has no real BLE radio.
- Auto-start on boot. BOOT_COMPLETED can't be sent from an unrooted shell.
- API 26-30 behaviour.

**Bugs fixed from the original draft:**
- The theme was `NoActionBar` with no Toolbar, so the overflow menu (Settings,
  Whitelist, Watchlist) could not be reached.
- The legacy `BLUETOOTH` and `BLUETOOTH_ADMIN` permissions were missing, which
  broke BLE on API 26-30.
- Only FINE location was requested. API 31+ ignores that unless COARSE is
  requested too.
- Denying the notification permission blocked scanning.
- Without the `location` FGS type, WiFi results and GPS tagging fail in the
  background. The service now falls back to `connectedDevice` when location
  isn't allowed, for example at boot.
- Every LOW_LATENCY BLE advert was inserted into the DB. Logging is now
  throttled to one row per MAC per 30s.
- The dedupe map and watchlist cache weren't thread-safe. Whitelist MACs weren't
  normalized, so entries never matched. CSV quote escaping was wrong.
- targetSdk 35+ edge-to-edge made content draw under the action bar. The fix is
  in `util/Insets.kt`.
- The default WiFi interval was 10s, which Android throttles almost every time.
  It is now 30s.

## Data flow (how a detection becomes an alert)
1. `BleScanEngine` (raw `BluetoothLeScanner`) and `WifiScanEngine`
   (`WifiManager` scan results via broadcast receiver) run inside
   `ScanForegroundService`, a `START_STICKY` foreground service.
2. Every result's MAC is checked against `OuiWatchlist.match()` — an
   in-memory map built from the enabled preset JSON assets plus any
   user-added custom entries (persisted in SharedPreferences as JSON).
3. On a match: check `WhitelistDao.isWhitelisted()` (skip if yes) → insert a
   `DetectionEntity` row into Room regardless (for the log/CSV export) → if
   not seen again within the configurable cooldown window, fire a
   high-priority notification via `NotificationHelper`.
4. `MainActivity` observes `DetectionDao.recent()` as a `Flow` and renders the
   live feed; export button dumps the full table to CSV via `FileProvider`
   and hands it to the share sheet.

## Known limitations to preserve in any README you write
- Phone BLE radios listen on fewer advertising channels with less gain than
  dedicated hardware (e.g. nyanBOX's triple-NRF24 setup) — expect a lower
  catch rate and shorter range than purpose-built hardware.
- `WifiManager.startScan()` is throttled by Android (a handful of calls per
  ~2 minutes outside a small allowance) — the foreground service helps but
  doesn't eliminate this.
- WiFi scanning only sees broadcasting access points, not client devices —
  so it mostly won't catch a laptop unless it's also acting as a hotspot.
- RSSI is not a reliable distance measure; `ProximityUtil`'s Near/Nearby/Far
  bands are explicitly coarse and said so in code comments.
